# Task Slices

## Purpose

Task slices segment a change into vertical behavior folders (`task-slices/<NN>-<slug>/`) so multiple engineers can work in parallel with less git conflict thrash on a single monolithic `tasks.md`. Slices hold narrative, technical contracts, per-slice tasks, and rollup-derived machine state.

## Current Behavior

A sliced change stores work under `wiki/changes/<change-id>/task-slices/`. Each slice folder contains:

- `slice.md` — human narrative (feat always; fix optional for trivial single-slice changes)
- `contracts.md` — slice-level technical contracts with adaptive sections (not FE/BE-only)
- `tasks.md` — horizontal tasks grouped by repo heading; per-task `Execution:`, `Repos:`, `Blocked by:`
- `status.yml` — stored metadata plus rollup-derived `status` and `task_summary`, and an optional `review:` block written only by `weave review`
- `review.md` and `review/` — the slice's code review record and run files, written only by `weave review record` (see [code-reviews](../code-reviews/behavior.md))

When two or more slices exist, `task-slices/dependency-graph.md` is auto-generated by the rollup library from per-slice `status.yml` files (`depends_on`, stored status, owner).

`weave-slices` scaffolds slice folders from upstream artifacts. `weave-fix` scaffolds a minimal fix-type slice (`tasks.md` + `status.yml`, optional `findings.md`). Legacy changes with only change-root `tasks.md` continue in flat mode.

## Domain Model

**Slice ID:** `<NN>-<slug>` (e.g. `02-admin-configures-approvers`). `status.yml.id` matches the folder name.

**Vocabulary:**

| Concept | Values | Where stored |
| --- | --- | --- |
| Slice status | `pending`, `in_progress`, `done` | `status.yml` (rollup-derived) |
| Derived slice state | `ready`, `blocked` | `dependency-graph.md` and rollup `ready_slices` |
| Ready for review | true when every active (non-`invalid`) task is `done` or `not_tested` | rollup `--json` `ready_for_review` (derived) |
| Slice review state | `in_review`, `reviewed`, `reviewed_with_rulings`, `waiting_on_person`, `skipped`, `review_failed`, `predates_review` | `status.yml` `review.state` (written by `weave review`) |
| Task status | `todo`, `in_progress`, `done`, `not_tested`, `blocked`, `invalid` | slice `tasks.md` |
| Task execution mode | `afk`, `hitl` | slice `tasks.md` (`Execution:`) |

**Coordination:**

- Within-slice task ordering: `Blocked by:` on tasks (within-slice only in v1).
- Cross-slice ordering: `status.yml.depends_on` (slice IDs). No cross-slice task deps in v1.
- A dependency lets dependents start when its rollup `status` is `done` while code review is inactive. While review is active it must also be ready for review and have a stored review state of `reviewed`, `reviewed_with_rulings`, `skipped`, or `predates_review` (`satisfiesDependents`). A slice waiting on a plan problem holds back every slice that depends on it.

## Behavioral Rules

### Scaffolding (`weave-slices`)

- Upstream by change type: feat → `prd.md` + `architecture/`; fix → `findings.md` + optional `architecture/`; chore/refactor → `exploration.md` + optional `architecture/`.
- Slice IDs allocated atomically in one pass; never renumber slices with `in_progress` or `done` tasks.
- Every task has explicit `Repos:`; `Owner:` left blank; `Execution:` defaults to `hitl`.
- Idempotent re-run: additive expansion only; never silently move `in_progress` or `done` tasks.
- After scaffolding: `weave slice rollup --all`, then `weave change progress slices`.

### Verification tasks (required per slice)

- Every slice must include explicit verification coverage.
- Prefer tests closest to changed behavior: unit, integration, request/API, component, E2E, migration/data, or regression as applicable.
- Verification task titles must name the behavior, boundary, or regression — not generic labels like "write tests".
- Automated verification uses concrete commands in each task's `### Verification` section.
- A step only a person can do goes on an optional `Human check: <step>` line under the task's `### Verification`. It is the only marker code reviews read for "needs your check"; a `Human check:` line anywhere else is not counted.
- When automation is impractical, add a dedicated manual verification task with numbered steps and expected result (`Execution: hitl` unless fully mechanical).

### Rollup library

Writer-derives model in `src/lib/sliceRollup.ts` with CLI `weave slice rollup [--slice] [--all] [--check]`. No editor PostToolUse hooks.

Triggers: end of `weave-execute` episode, HITL pause, error exit, after `weave-slices` / `weave-fix` scaffolding, manual CLI.

Defensive parse: malformed partial `tasks.md` does not overwrite valid existing `task_summary`. Cycle in `depends_on` writes a WARNING banner; primary writes still succeed.

- **Review state is carried, never written.** Rollup keeps a slice's `review:` block unchanged (absent stays absent). It never derives or stores review state; out of date is computed by readers.
- **Locking.** Each slice's read-modify-write runs under the per-change lock shared with `weave review`, and slice files and the dependency graph are written atomically, so a concurrent review write is never lost.
- **`--check` writes nothing.** `weave slice rollup --check` reports whether derived state is stale without writing slice files, the graph, or review adoption. A change in `updated_at` alone, or in the graph's "Generated at" line alone, is not a change, so an unchanged slice is not rewritten and `--check` can report no change.
- **JSON readiness.** Each slice result carries `ready_for_review` (true even while `status` stays `in_progress` because a task is `not_tested`). The change result carries `ready_slices`: `pending` slices whose dependencies all let dependents start under the rule above. `ready_slices` is current even when `--check` reports `check_failed`.
- **Review gating.** Rollup uses review gating only when code review is active for the change. The first non-check rollup with review active adopts the change for review (stamps `adopted_at` and `predates_review` on slices already ready for review). With review active, `dependency-graph.md` adds "With code review on, each of those slices must also be reviewed." and its ready, blocked, and parallel-work sections use the same rule.

### Dual-mode dispatch (`weave-execute`, `weave-next`)

- `task-slices/` exists → slice mode (`/weave-execute 01 T1`, `/weave-next afk`). Both skills read the slices that may start from rollup's `ready_slices` (`weave-next` uses `weave slice rollup --all --check --json`, which writes nothing) instead of computing readiness from `depends_on`.
- Only change-root `tasks.md` → flat legacy mode (`/weave-execute T1`, `/weave-execute all`).
- No forced migration tool for legacy flat changes.

## Lifecycle

Artifact lanes (change-type dependent):

- feat: `exploration` → `prd` → `architecture` → `slices`
- fix: `findings` → optional `architecture` → `slices`
- chore/refactor: `exploration` → optional `architecture` → `slices`

CLI accepts `weave change progress slices`; `issues` is a legacy alias normalized to `slices` on read.

## Integrations And Side Effects

- `weave-prepare` is deprecated; branch prep is absorbed into `weave-execute` (still calls `weave task prepare` internally).
- `weave-issues` removed from bundled templates; replaced by `weave-slices`. Existing installs may retain stale `weave-issues` until `weave agent install all`.
- Skill install: bundled templates ship in npm `templates/`; repo-local copies require `weave agent install`. `weave agent update` refreshes existing manifest entries only — new skills (`weave-slices`, `weave-fix`, `weave-review`) need `install`, not `update` alone, and `update` never adds resource files for a skill the agent has not installed. The `skills_available` notice names bundled skills a configured agent is missing.
- Code reviews: see [code-reviews](../code-reviews/behavior.md) for slice reviews, the final review, and how review state gates dependents.
